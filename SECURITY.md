# Политика безопасности проекта

## Поддерживаемые версии

Актуальная ветка — `main`. Исправления безопасности выходят в минорных
релизах; старые минорные версии не поддерживаются.

| Версия | Поддержка |
|---|---|
| 0.1.x | да |

## Как сообщить об уязвимости

**Не открывайте публичный issue.** Напишите приватно:

- GitHub → вкладка **Security** → **Report a vulnerability** (приватный
  security advisory), либо
- письмо мейнтейнеру, указанному в профиле репозитория.

В сообщении полезно указать:

1. Версию и файл, где воспроизводится проблема.
2. Минимальный сценарий: входные данные, команда, ожидаемое и фактическое
   поведение.
3. Оценку последствий: утечка данных, выполнение кода, обход проверки.

Ответ в течение 5 рабочих дней. Публичное раскрытие — после исправления и
согласования сроков.

## Модель угроз инструментов

Скрипты работают локально и читают файлы, которые им передали. Основные риски,
которые мы рассматриваем:

| Риск | Что делаем |
|---|---|
| Внедрение в отчёт (CSV/HTML-инъекция) | Экранирование HTML через `HtmlEncode`, CSV через штатный writer |
| Утечка чувствительных данных в отчёт | Отчёты не содержат паролей и токенов; документация требует обезличивания |
| Неожиданное изменение системы | Аудит только читает; никаких `Set-*` и `New-*` для настроек |
| Обращение к сети | Нет ни одного сетевого вызова |
| Повышение привилегий через входные данные | Регулярные выражения без бэктрекинга, ограничение размеров буферов |

## Что не является уязвимостью

- Ложные срабатывания правил обнаружения — это настройка порогов, а не
  дефект безопасности.
- Пропуск проверки аудита без прав администратора — ожидаемое поведение.
- Отсутствие поддержки конкретного формата журнала — вопрос функциональности,
  создавайте issue.

## Требования к участникам

- Не добавлять зависимости без обсуждения: проект сознательно живёт на
  стандартной библиотеке.
- Не добавлять сетевые вызовы и телеметрию.
- Не включать в тесты реальные IP-адреса, имена хостов и хеши.
